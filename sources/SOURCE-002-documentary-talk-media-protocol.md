# SOURCE-002 — 纪录片 / 演讲 / 媒体的游戏史核验协议

- Type: Source Method
- Status: ACTIVE
- Applies to: 《独立游戏英雄传说》《斯拉夫游戏英雄传说》及共享 Case / Claim / Evidence

## 1. 为什么单独建立这套协议

作者早期形成大量游戏史知识时，纪录片是重要入口；后续研究不能把这些知识丢掉，也不能因为“在纪录片里看过”就直接视为已核事实。

纪录片、开发者演讲、postmortem、同期媒体采访，本质上是不同证据形态的容器。关键不是媒介名称，而是：**具体一句话由谁说、何时说、基于什么材料、是否能够追到同期记录。**

## 2. 纪录片不是单一证据等级

同一部纪录片中的不同片段可以属于不同等级：

- 当事开发者的同期采访录像 / 当时录音：按内容可视为 **P0**；
- 当事开发者多年后的回顾性口述：**P1**；
- 导演或旁白对历史的解释：通常为 **S1 / S2**，取决于是否有明确采访、档案与编辑基础；
- 影视化重演、无来源数字、为戏剧效果压缩的因果链：只能作为线索，不能承担关键结论。

因此禁止写“纪录片证明了 X”。应写成“纪录片中某位当事人在某时间点声称 X”，或“纪录片旁白给出 X 解释，尚待同期资料核验”。

## 3. 开发者演讲 / GDC / postmortem

开发者本人、创始人、制作人、工程负责人等在会议或公开演讲中的材料优先级很高，但仍要看时间与角色：

- 项目开发期或发售前后、由直接参与者讲述的开发事实：优先按 **P0**；
- 多年后的复盘：**P1**；
- 公司 PR 演讲：仍是一手材料，但必须记录其利益相关性；
- 演讲中的行业普遍化结论不能自动从“当事人经验”升级成总体事实。

## 4. 专业媒体

媒体采访需要拆成两层：

- 被采访者直接引语 / 明确归因的事实：根据被采访者身份与时间，可作为 P0/P1；
- 记者自己的历史归纳：S1 或 S2。

应优先保存原始采访、视频、逐字稿、刊发日期，而不是只引用后来引用它的 Wiki 或整理文章。

## 5. 默认检索顺序

对于游戏史、工作室史和产品形成史，默认同时搜索以下来源，而不是只做网页文章检索：

1. 开发者同期采访、开发日志、公司原始公告；
2. GDC / Devcom / Gamescom / Gamelab / 本地开发者会议等公开演讲与 postmortem；
3. 同期专业媒体采访与专题；
4. 高质量纪录片、电视专题、口述史；
5. 公司周年纪录片与官方历史页；
6. 多年后的长访谈、书籍与回忆；
7. Wiki、论坛、Reddit、视频整理仅用于发现线索。

纪录片不是“低等级来源”；它常常是**定位被遗忘的一手证词和人物关系的高价值入口**。但关键结论应尽量回追到更接近事件发生时的材料。

## 6. 视频 / 纪录片 Evidence Record 必填字段

- Title
- Producer / Publisher
- Recording date（若可知）
- Publication date
- Speaker / Interviewee
- Speaker role at the time
- Timecode
- Claim / quote summary
- Direct testimony / narration / archival footage
- Evidence class
- Original source shown or cited in the film（若有）
- Corroborating sources
- Contradictory sources
- Notes on editing / retrospective bias

## 7. 作者旧知识的处理

若作者记得某个游戏史事实“来自某纪录片”，但一时无法确认片名：

- 先记录为 **A0-SOURCE-MEMORY**；
- 不将其写成事实；
- 优先反查纪录片、相关人物演讲与同期媒体；
- 找到后再升级为 P0/P1/S1/S2。

目标不是否定作者过去的知识来源，而是把当年的观看经验转换为**可追溯、可复核、可纠错的研究链**。
