# Reader Profile Editorial Gate

本 Gate 属于 **Lane C / Editorial**，但由 Lane A 维护其流程边界。它不创造事实，也不替代 Case / Evidence / Claim。

目的：让 reader profile 真正成为“人物与生产史”，而不是把研究档案换成更顺的论文。

## -1. 先判断你在写 Profile 还是 Chapter

**Profile** 的主角是一个人 / 团队，核心问题是：

> 他 / 他们怎样走到这里？

**Chapter** 的主角是一个现实问题，核心问题是：

> 多个人生放在一起，能让读者更清楚地判断什么？

Chapter 必须做到：
- 至少比较两个已进入 reader layer 的人物 / 团队；
- 不能按“案例 A、案例 B、案例 C”机械摘要；
- 必须存在冲突、反例、边界或不同路径；
- 结论必须比任何单个 Profile 更一般，但不能超过 Claims / Evidence 支持范围；
- 面向非游戏行业读者时，先翻译成人生问题，再保留游戏产业细节。

若只是把 Case 散文化，既不是合格 Profile，也不是合格 Chapter。

---

## 0. 事实边界先于文风

- 关键事实必须能回指 Case / Evidence。
- 不得为了场景感补写 UNKNOWN。
- 不得虚构对话、动作、心理、地点细节或时间顺序。
- P1 回忆必须保持“多年后回顾”的性质，不倒写成同期已知。
- 任何书级 Thesis Candidate 都不能因为文章需要高潮而写成已证实规律。

若叙事需要的细节不存在，宁可写得克制，也不要小说化补洞。

---

## 1. 先让读者遇见人，再让读者遇见理论

Profile 的开头优先让读者看到：

- 一个具体时刻；
- 一个具体处境；
- 一个具体选择；
- 一个具体矛盾；
- 或一个足以改变生产路径的事实。

不要默认从：

> “独立游戏史经常把这个故事讲成……”

起手。

“流行神话 → 反驳神话”仍然可以使用，但不能成为所有 profile 的统一模板。

如果证据允许，前 300–500 字应尽量出现至少一个**人 + 决策/处境**，而不是只出现项目 thesis。

---

## 2. 每篇只保留一个主命题

一篇 profile 可以触及多个 Claim，但 reader layer 需要一个清楚的主问题。

写作前先完成一句：

> “这篇主要回答：________？”

例如：

- Kenshi：一个明显超过单人正常产能的项目，什么时候开始不再只靠一个人的生命时间供养？
- Rocket League：一家公司怎样用服务业务购买组织存续，并保留第二次原创下注的权利？
- FTL：团队怎样把一次高风险创业拆成逐步增加承诺的实验？

次级命题必须服务主问题，不要每一段都重新宣布一个“大结论”。

---

## 3. Reader layer 要少说“研究正在做什么”

以下语言属于 research backend 的正常语言，但在 reader profile 中高频出现会破坏叙事：

- “本案最值得研究的是……”
- “当前证据支持……”
- “从生产史角度看……”
- “真正重要的是……”
- “这个案例证明……”
- “Evidence Ledger 显示……”

这些词不是禁词，但应优先转成：

> 人当时面对什么 → 做了什么 → 直接发生了什么 → 我们为什么因此改变理解。

研究状态、UNKNOWN、证据等级应集中放在 provenance / research boundary 区，而不是不断插入正文。

---

## 4. 控制“不是……而是……”和结论句密度

当前样稿反复依赖：

- “不是 X，而是 Y”；
- “真正的故事不是……”；
- “真正值得记住的是……”；
- “这很重要”；
- “换句话说”。

这种结构适合纠正 Myth，但高频会让五篇文章拥有同一个说话节奏。

编辑时检查：如果连续几个小节都以否定旧解释、宣布新解释推进，至少重写一部分为**时间推进、行动结果或具体矛盾**。

---

## 5. 专有研究词必须先翻成人话

可以使用：`runway`、`scope`、`market access`、`capability capital`、`staged commitment` 等术语，但第一次出现必须先让普通读者知道它具体指什么。

优先写：

> “还能不接别的工作、继续做这个游戏多久”

再告诉读者这就是这里说的 `runway`。

不要连续使用多层抽象词，例如：

> “capability capital 改变 production function，并通过 market-access infrastructure 转成 organization capital”。

研究档案可以这样压缩；书稿不应该要求读者先学术语才能理解故事。

---

## 6. 把具体行动写在人格判断前面

坏：

> 他很有品味。  
> 团队很灵活。  
> 他们非常坚持。

好：

> 他删除了哪些昂贵但不服务核心体验的内容；  
> 团队把 full launch 改成 demo；  
> 公司继续接 work-for-hire，让合同项目覆盖原创团队；  
> 开发者用付费 alpha 把玩家收入换成下一阶段人力。

如果一句人格描述不能被至少一个具体行动支撑，应删掉或降成作者判断。

---

## 7. 跨案例综合不要侵占每篇结尾

Profile 的结尾优先回到：

- 这个人 / 团队；
- 本篇主问题；
- 这一案的 transfer boundary。

不要每篇都在最后重新串一次 Kenshi / FTL / Rocket League / Gunpoint / 其他案例。

跨案例综合主要放在：

- 章节导语；
- book-level synthesis；
- `THESIS-CANDIDATES.md`；
- 最终 TOC / thematic chapter。

个案偶尔引用另一案做对照可以，但不应把 profile 变成全书 thesis 的证明段落。

---

## 8. Provenance 与叙事分层

每篇必须保留 Case / Evidence 回链，但建议分成两个层级：

### 顶部最小 provenance

- 对应 Case；
- Evidence Ledger；
- 必要时一句当前状态。

### 文末 research boundary

集中列：

- 仍 UNKNOWN；
- 关键证据；
- 不可直接复制条件；
- 尚未解决的因果问题。

不要让同一研究状态免责声明在正文中反复出现。

---

## 8.5. 所有“值得学”都必须有年份与时效性

Reader layer 一旦从历史事实推出“今天可以学什么”，必须同时回答：

- **Observed When**：这个做法真正发生在什么年份；
- **Regime**：当时的平台、工具、发行、支付、社区、竞争与成本条件；
- **2026 Transfer Status**：`DURABLE / CONDITIONAL / HISTORICAL / CURRENT / UNKNOWN`；
- **Mechanism vs Tactic**：今天保留的是结构机制，还是某个已经过期的渠道打法。

禁止把“2019 年成功经验”写成无日期的通则。

平台 / 算法 / 商店曝光 / creator discovery / 众筹 / 生活成本 / 融资环境属于高时效变量；未做当前核验时默认 `CONDITIONAL / UNKNOWN`。

完整规则见 [`TEMPORAL-VALIDITY.md`](TEMPORAL-VALIDITY.md)。

---

## 9. 场景化不等于小说化

优先使用已有证据中的具体东西：

- 时间；
- 工作岗位；
- 数字；
- 公开开发日志；
- 决策节点；
- 当事人同期说法；
- 产品当时的状态；
- 失败后的实际动作。

禁止补写来源没有的：

- “他坐在昏暗办公室里”；
- “他当时一定感到绝望”；
- “两人对视后决定赌上一切”；
- 未核验的日常细节。

好的生产史靠**决策细节**产生戏剧性，不靠虚构文学细节。

---

## 10. 发布前人工检查

每篇 profile 升级前至少问一次：

1. 前 500 字能看到“人和处境”吗？
2. 能用一句话说清这篇主问题吗？
3. 是否连续三次以上用 Myth → 反转 → thesis 推进？
4. 是否研究术语比具体行动更密？
5. 是否为了叙事补了 Case 没有的细节？
6. 文章是否把同一个 thesis 说了三遍以上？
7. 结尾是在结束这个人的故事，还是又替整本书写总论？
8. UNKNOWN / transfer boundary 是否仍然清楚？
9. Case / Evidence 回链是否存在？
10. 这篇和上一篇在开头、节奏、结尾上是否明显不同？
11. 所有可迁移经验是否写明观察年份和 2026 时效状态？
12. 是否把某个历史平台 tactic 误写成 timeless mechanism？

## Automation boundary

当前 Gate **不进入机械 lint**。

原因：以上问题多数依赖语境和叙事判断。只有未来出现明确、重复、可机械识别的错误（例如 provenance 缺失、链接漂移、固定字段缺失），才升级为工具 / CI。

## 11. 研究元数据下沉，不占读者第一屏

Profile / Chapter 第一屏原则上不出现：
- CASE 编号；
- Evidence Ledger；
- RESEARCHING / SKELETON；
- P0 / P1 / S1 / S2；
- lint / schema / metadata。

这些信息原则上集中到文末的“研究与证据入口 / 研究依据”。

例外只有一种：某个研究状态本身直接影响读者如何理解正文，例如关键争议尚未解决。这时也应先用人话说明，不要先抛后台术语。

Reader layer 的目标不是隐藏证据，而是让证据待在正确的位置。
