# 056 — AI 前端界面反模板审校：面向未来 HTML 书稿的视觉验收参考

- **Status:** METHOD REFERENCE / PRE-CLAIM

## 0. 应用边界｜严格限制到 HTML 书稿的界面呈现

本 Skill 的 **UI** 指数字产品界面，而不是书稿语言、人物传记写作或 LLM prose。所谓“AI 味”指布局、配色、排版、导航、组件、交互状态、动画等视觉/前端模板痕迹，**绝非 AI 写作腔**。

**未来可用**：HTML 版书稿网页、章节阅读器、目录导航、时间轴、人物/案例索引、可视化对照表、网页封面与移动端阅读布局；前提是相关呈现任务进入实际设计/实现阶段，先做一个真实章节的代表性页面，验证阅读连续性、信息密度、视口与可用性，再扩展全书。

**明确不适用**：纸面或 Markdown 正文写作、作者与人物叙事声线、章节结构的内容判断、史实核验、AI 写作 Humanizer / 防 AI 文风、资料采集、传记和研究论证。即使最终在 HTML 网页中显示，正文内容本身仍由既有资料/写作/核验 Owner 负责；此 Skill 只能改善其视觉呈现，不能擅自改写正文。

**边界规则**：排版可决定换行、字体角色、宽度、信息的屏幕呈现和辅助导航，但不能为了填满卡片、满足设计构图而扩写段落、删掉有意义的事实、制造统计数字，或把文字稿改成“UI 微文案风格”。必要的 UI 操作标签（如“下一章”“返回目录”）属于界面功能用语，不等于允许重写叙事文本。

## 2. 方法的主要贡献

### 2.1 “反模板”应描述模式，而非只禁止 token

Skill 指出：只禁止某个颜色、字体或圆角值，模型可能换成视觉上几乎相同的近似值。应识别组合模式，例如所有区域使用同一种卡片、没有产品依据的渐变、通用的标题装饰、为凑密度而缩小文字等。

可迁移的做法是把“不要这样”写成**可被实际成品识别的模式描述**，并允许真实需求推翻默认禁令。清单应由项目第一次渲染后的新问题持续补充，而不是一次写成普遍美学法典。

### 2.2 先建立产品事实，再选视觉方向

在动手前读取真实内容、目标用户、反复执行的任务、现有设计系统、素材、视口与行为约束；区分已验证信息和计划中的假设。再确定界面属于表达型、内容型还是操作型，提出具体方向，说明证据、构图、层级、密度、字体 / 颜色角色，以及拒绝了哪种最容易套用的方案。

“有辨识度”不是随便找一套少见的配色。方向必须从产品自身的对象、用途和环境推出。

### 2.3 先做最小代表性切片，再扩展

先做一个足以暴露设计系统问题的真实页面 / 视图：有代表性的内容密度、主要动作、导航和关键状态。先渲染、检查、修正最大缺陷，再扩展到全量实现。这能把视觉方向错误的返工成本限制在较小范围。

### 2.4 视觉评审与代码评审分离

作者建议评审者先看实际渲染图，再读源代码和作者解释；若没有独立评审者，则将冷读和任务 walkthrough 分成两轮。评审应回答第一、第二、第三视觉重点是否正确，视线在哪里停滞，页面是否可以被另一个产品轻易换标复用，以及移动端是否真的重新组织了信息。

这不是要求每个项目都用同一套审美，而是要求评审先观察证据，再解释设计意图。

### 2.5 “截图生成”与“视觉验证”不是同一件事

该 Skill 要求打开并实际检查截图；对窄屏还要读取页面实际布局宽度并确认断点生效，不能仅凭 PNG 文件的尺寸声称移动端已通过。报告应写清检查过的视口、状态、发现、未检查范围和最终判断。

它把功能信心与视觉信心分开：

- **功能已验证：** 代码、交互和相关行为实际经过测试。
- **视觉已验证：** 实际渲染的图像已被打开、观察和批评。
- **未进行视觉验证：** 图像无法检查或未实际查看，必须如实保留这一状态。

### 2.6 交付说明要区分真实功能与模拟功能

如果数据是硬编码的、请求只是定时器模拟、流程只能单向运行或图像仍是占位素材，交接时要明确标出。一个原型可以合理地使用模拟内容，但不能把模拟效果描述成已完成的生产功能。

## 3. 对未来 HTML 书稿与游戏前端呈现的可迁移假说

1. **实现能力与视觉判断是不同能力。** 构建成功、测试通过或实现复杂，并不能单独证明成品具有清晰层级、产品辨识度或良好可读性。
2. **视觉质量需要独立的现实反馈回路。** 如果作者只阅读自己的 CSS、设计说明或生成日志，缺陷可能长期留在代码之外；实际渲染、冷读和复核是另一条验证路径。
3. **最便宜的高价值验证是尽早暴露最大错误。** 先验证代表性切片的视觉方向，比完成整套界面后才发现方向错了更容易回退。
4. **“避免 AI 味”需要正向的产品特异性与负向的模式诊断共同工作。** 只给负面清单可能让模型改用另一套模板；只说“有个性”则没有可执行标准。
5. **报告必须暴露证据覆盖范围。** 没检查的视口、状态和流程不能被含混地归入“已经验收”。

这些只是从 UI/前端工作规程中抽取的可检验方法假说。对本书主要应用目标是未来 HTML 阅读页面的视觉质量和交互可用性，并不对书稿文学质量、写作原创性或行业结论产生判断力；也不是该 Skill 已被证明能提高销量、留存、转化率或玩家评价的结论。

## 4. 不应照单全收的部分

- **固定数值不是普遍定律。** 动画时长、圆角、间距、字体和缩放值可以作为初始默认，但必须由实际任务、技术栈、输入设备与渲染结果验证。适用的无障碍标准应按其标准本身核对，不应把所有数值都视为该 Skill 独创的最佳实践。
- **模式禁令不能取代设计判断。** 卡片、胶囊按钮、衬线字体、渐变或极简布局在合适的产品中都可能成立。Skill 本身也允许在真实 brief 有要求时采用这些模式；关键是它们是否有产品依据。
- **它主要针对 Web / 前端 UI。** CSS 动画、响应式断点、表单验证与窄屏布局不能原样套到所有游戏 HUD、像素美术、战斗读屏或宣传镜头。
- **公开自述不等于效果评估。** 该文档本身没有提供独立对照实验、系统的用户研究或可核对的产品结果数据。因此它能作为方法来源，不能单独承担“这套流程一定有效”或“AI 界面普遍如此”的事实主张。
- **不应据此生成固定的 AI 禁词表。** 实际验收要针对成品的构图、信息层级、内容真实性、可读性和行为，而不是通过词语命中率或机械打分替代评审。

## 5. 后续研究问题

如果要把它升级为正式 Claim，需要寻找真实项目的前后对照或独立评估，至少比较：

- 是否在首轮实现前定义产品事实与视觉方向；
- 是否进行代表性切片渲染和独立冷读；
- 返工时间、可发现缺陷、可读性 / 可用性结果如何变化；
- 改善来自工作流本身，还是来自参与者经验、设计资产、审查时间或工具差异；
- 哪些界面类型 / 团队规模 / AI 工具组合能复现效果，哪些不能。

在取得这些证据之前，保留为方法参考，不进入书稿定论，不推导行业发生率，也不推导 AI 工具优劣排名。
