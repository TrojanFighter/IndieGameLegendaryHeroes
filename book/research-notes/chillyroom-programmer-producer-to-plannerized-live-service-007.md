# 凉屋内部制度对照：programmer-producer 与 hybrid plannerized live-service

- Status: RESEARCH NOTE / WITHIN-FIRM COMPARATOR / NOT A FORMAL CLAIM
- Last verified: 2026-10-06
- Scope: 凉屋游戏如何在保留自下而上、小队原型与制作人 ownership 的同时，叠加专职玩法、数值、经济策划与 live-service 职能
- Related: `china-commercial-game-training-role-origin-audit-005.md`, `CASE-028 Chinese Online Game`
- Claim status: **NOT A FORMAL CLAIM**

## 0. 研究问题

Role-Origin Audit 的一个关键难题是：如果只把人按“程序 / 策划”分桶，很容易把真正的制度变量漏掉。

凉屋提供了一个罕见的同公司纵向对照：

> **早期凉屋公开采用“程序/美术可立项、通常程序制作人、无专职策划、设计者亲自实现”的小团队结构；而当前凉屋已经形成专职玩法、数值、经济、角色等策划岗位，并运行具有赛季、长期成长与应用内购买的 live-service 产品。**

因此更值得研究的不是“程序员和策划谁更会设计”，而是：

> **同一公司在团队规模、收入接口、live-service obligation 和岗位分工改变后，设计者所面对的反馈函数如何改变。**

---

## 1. 2017–2019：早期凉屋的 programmer-producer regime

2017 年凉屋团队公开说明：

- 公司当时约 10 人；
- 单个项目通常只有 1–3 人；
- 团队任何成员都可以做 prototype；
- 原型验证有效，就可能成为自己的正式项目；
- “通常是程序作为制作人，把握整个游戏的感觉”；
- 立项最初优先考虑自己擅长什么、想做什么，而不是先做市场模型。

2018 年凉屋官方博客进一步把这种制度说得更明确：

- 当时没有专职策划岗位；
- 程序、美术、文字等单项技能之外，成员需要把游戏作为整体思考；
- 不依赖强顶层规划和厚策划文档，而采用增量迭代；
- 设计者最终要把自己的设计真正做出来，因此工作量与制作难度会直接反馈进设计判断；
- 官方甚至用 “eat your own dog food” 来描述这种责任闭环。

2019 年公开采访仍然说明：凉屋扩张时引入的制作人有美术背景、有程序背景，“唯独没有策划”；团队认为好的主意应由制作人以美术或程序角色亲自实现。

### 当前读法

这是一个非常清楚的 **high prototype authority + high cost visibility + broad ownership** 制度。

它不能证明程序员 taste 更好，但它说明：

> **程序员如果同时被制度赋予产品定义权、原型权和删改权，他接受的训练就不再只是“实现别人的策划案”。**

## 2. 当前凉屋：专职策划重新出现，但早期小队制度没有被替换

当前凉屋官网与招聘页面已经出现明确的专业策划岗位：

- 游戏策划；
- 主策划 / 资深数值策划；
- 角色设计方向策划；
- 《元气骑士》项目策划；
- 《元气骑士前传》项目玩法策划。

其中当前主策 / 资深数值岗位公开职责包括：

- 与制作人共同确定设计方向；
- 系统、数值、经济框架；
- 分析运营数据与玩家行为；
- 游戏生命周期与付费模式；
- 策划团队管理。

《元气骑士前传》的项目定向玩法策划岗位则直接包括：

- 核心玩法规则；
- 核心机制；
- 数值框架；
- 关卡逻辑；
- “易上手、高留存”的玩法体验。

这说明当前凉屋的 production regime 已经不能再用 2017 年的“没有专职策划”描述。

2026 年 4Gamer 对李泽阳的采访又补上了关键反压力：公司虽已接近 200 人、同时运行十条以上开发线，但大部分项目仍由员工主动发起，管理层自上而下推动的项目不多；新项目通常只有 4–5 人起步，产品跑起来后再增加成员。也就是说，凉屋没有简单从 author-driven 小队“转型成”传统职能制大团队，而是形成了**小队自组织 + 专业职能叠加**的混合结构。

因此这里的纵向变化应写成 **hybridization**，而不是 linear replacement：

```text
早期：1–3 人、无专职策划、programmer/artist-producer
↓
规模扩大、live-service obligation 增加
↓
当前：4–5 人起步的自组织项目仍保留
     + 专职玩法 / 数值 / 经济 / 文案等策划
     + 赛季、经济、长期运营、数据反馈职能
```

### 重要边界

这不等于凉屋放弃制作人主导，也不等于现代凉屋是传统大厂结构。

公开材料仍显示凉屋强调小团队、员工自发立项、制作人 ownership 和 prototype 文化。

更准确的表述是：

> **原有的 author-driven producer model 没有消失，而是在更大的组织中与专业化策划、长期运营、经济系统与数据反馈职能并存。**

## 3. 产品级对照：《中国式网游》 vs 《元气骑士前传》

这个对比不是“谁更好玩”的主观评分，也不是“某个策划个人 vs 某个程序个人”的能力排名。

它只比较两种 production objective 在产品结构上的可观察差异。

| 维度 | 《中国式网游》 | 《元气骑士前传》 |
|---|---|---|
| 核心生产结构 | solo core；作者自述策划、程序、简单美术大量工作一人承担 | 项目仍可能从 4–5 人自组织小队起步，但成熟 live-service 线已拥有玩法、数值/经济等专业岗位 |
| 商业接口 | premium / 买断制单机 | 移动 live-service；包含广告与应用内购买 |
| 时间结构 | 有限作品，把长期网游经验压缩成单机流程 | 赛季持续更新、长期回流与成长 |
| progression | 充值、成长、排行榜、活动等被转换为模拟/讽刺对象 | 职业、技能、装备、羁绊、专精、赛季等构成真实长期成长系统 |
| 内容 obligation | 作品完成后不需要持续多年维护一整套真实 MMO economy | 需要长期内容、平衡、赛季、线上服务和经济维护 |
| 设计反馈 | 单一作者直接承担 scope 与实现成本 | 制作人 + 专业岗位 + 运营数据 / 玩家行为形成多节点反馈 |
| retention | 不是产品结构上的长期服务目标 | 当前项目招聘明确把“高留存”写入玩法目标 |

### 3.1 最有意思的反转：《中国式网游》不是“不懂 F2P”

它的核心恰恰是高度理解 F2P / 中国网游语言：

- 充值；
- 战力；
- 排行榜；
- 养成；
- 活动；
- 消费心理。

但这些元素被重新编码：

> **原本用于维持真实付费与长期运营的系统语法，被变成一次购买后供玩家体验、识别和讽刺的内容。**

因此它更适合作为 **Domain Knowledge Inversion**：

不是“不懂商业游戏”，而是把商业游戏知识反过来使用。

### 3.2 《元气骑士前传》则是真实承担 live-service obligation

公开商店页面显示：

- 广告与应用内购买；
- 多人联机；
- 长期赛季更新；
- 多职业与混合职业；
- 大量装备与羁绊组合；
- 持续扩展的养成和新内容。

这类产品自然需要：

- economy；
- progression；
- balance；
- retention；
- content cadence；
- player-behavior feedback。

因此专职策划岗位出现并不奇怪。

## 4. 这个同公司对照支持什么

当前最合理的命题是：

> **岗位分工不是独立变量。商业模式、团队规模和长期服务义务会共同决定一个组织需要什么样的设计岗位，并进一步训练这些岗位反复解决什么问题。**

早期凉屋的程序制作人被反复训练的是：

- 能不能快速做出来；
- 核心交互是否成立；
- 这个 feature 值不值得自己的实现成本；
- 小团队能否完成。

hybrid plannerized live-service 项目中的专业岗位则更频繁面对：

- 数值经济是否稳定；
- 长期成长是否成立；
- 新内容怎样接入既有系统；
- 玩家行为与留存如何变化；
- 赛季与付费结构怎样持续运转。

两组能力都是真实专业能力。

研究问题是：

> **当人从后一种环境突然进入极小团队 premium 项目时，哪些训练可以直接迁移，哪些默认解法需要主动卸载？**

## 5. 这个对照不能支持什么

### 5.1 不能说“凉屋有策划以后游戏变差”

当前没有这样的因果证据。

产品类型、团队规模、用户规模、平台和商业模式全部同时变化。

### 5.2 不能说“程序员做的都是纯独游，策划做的都是商业套路”

早期凉屋本身就是特殊制度；程序在这里经常同时承担制作人与设计责任。

当前凉屋的玩法策划岗位也要求参与核心玩法落地，并非只做表格。

### 5.3 不能把《元气骑士前传》称为“策划作者作品”

公开证据只能证明：

- 当前该项目存在专职玩法策划岗位；
- 凉屋当前存在数值 / 经济 / 系统策划专业化；
- 产品属于实际 live-service 结构。

它不能证明某一名专职策划是该产品的唯一创意作者。

因此本研究使用 **plannerized product / plannerized production regime**，而不是 **planner-authored game**。

---

## 6. 对 Role-Origin Audit 的新变量

凉屋这个纵向对照要求 Role-Origin Dataset 增加几个字段：

1. **organization regime at time of employment**
   - no-dedicated-planner
   - prototype/incubation
   - traditional functional specialization
   - live-service specialization

2. **producer architecture**
   - programmer-producer
   - artist-producer
   - planner-producer
   - dedicated producer + functional planners

3. **service obligation**
   - fixed premium
   - early access
   - seasonal live-service
   - MMO / persistent economy

4. **implementation accountability**
   - 设计者是否亲自实现
   - 是否需要通过独立执行岗位
   - feature 成本多久反馈回提出者

5. **metric exposure**
   - 主要反馈来自 playtest / feel
   - 还是 DAU / retention / economy / payer segmentation
   - 或两者都有

这样才能避免把“在凉屋做程序”和“在大型 F2P 公司做客户端基础设施程序”误编码成同一个 treatment。

## 7. 下一步证据缺口

1. 凉屋从“无专职策划”到建立专业策划岗位，大致发生在哪一阶段？
2. 哪些具体项目最早出现专职玩法 / 数值 / 经济策划？
3. 《元气骑士》《战魂铭人》《元气骑士前传》各自主创的原岗位和 ownership span 如何变化？
4. programmer-producer 项目与 plannerized 项目在 prototype latency、feature deletion、meta 层数和内容 cadence 上是否存在稳定差异？
5. 是否能找到离开凉屋的程序、美术、策划分别独立制作作品的更多 alumni 样本？

## 9. 当前结论边界

截至 2026-10-06，这个 within-firm comparator 最多支持：

> **同一开发公司可以在保留小队自组织与制作人 ownership 的同时，因商业模式、组织规模与 service obligation 增加而叠加专业策划职能；因此“程序 / 策划”职位标签本身不足以解释独立游戏能力迁移。**

它尚不能支持：

> “专职策划制度导致产品质量下降”；

也不能支持：

> “程序员制作人制度在所有游戏类型上更优”。

后续需要具体 alumni、项目 credits 与失败样本继续检验。
