# Reader-layer build notes

这不是研究结论，也不是最终书稿；它记录《独立游戏英雄传说》从研究数据库长成可读作品时采用的构建原则，避免同一类信息架构问题反复讨论。

## 2026-10-04：从 HowToLiveBetter 提交史得到的工程启发

对 `eternity4719/HowToLiveBetter` 的公开提交史复盘显示，它的成熟形态并不是一开始设计完成的。几个关键阶段是：

1. **先钉 schema 和证据规则，再批量生产内容。** 初始提交先建立统一条目格式、证据分级、来源规则和最小目录；二十分钟后一次写入首六节 87 条正文与核实记录。
2. **内容一有规模，就立刻做消费界面。** 项目建立不到一小时即增加 GitHub Pages 检索页；同日 README 已有问题索引、徽章、SEO 和分享图。
3. **物理目录随真实瓶颈演化。** `book/` 并非 Day 1 预设；正文单文件长到 531 KB、超过 GitHub Markdown 渲染上限后才按节拆分。
4. **把真实错误变成规则和工具。** 统计数字漂移催生同步脚本；插条目导致交叉引用错位催生引用对照和 CI；“说人话”引入正文没有的事实后，规则被写回 CLAUDE.md。
5. **单一事实源优先。** 后来的 skill 不再复制整套章节与算法，而是读取 README / index 的权威结构，减少多份路由表漂移。
6. **面向读者的 view 不应复制 canonical 内容。** 场景清单和 skill 负责路由、组合和解释，正文仍是事实源。

这些是公开 Git 历史能够支持的结构结论。私有 Claude Code 对话不可见，因此不能把具体对话内容当作已知事实；但提交信息中大量保留“用户定 / 读者提出 / 规则写回”的痕迹，说明仓库规则明显经历了持续的人—Agent 反馈沉淀。

## 对本仓库的直接约束

### Research backend 是 canonical

- `metadata/`：机器事实索引；
- `cases/`：案例研究事实与边界；
- `evidence/`：来源与证据能力；
- `claims/`：跨案例命题。

`book/` 不重新发明上述事实。

### Reader layer 是 view

`book/` 的职责是改变阅读顺序、叙事密度与问题入口，而不是建立第二套 Case registry。

每个 profile 必须：

- 回链一个正式 Case；
- 回链对应 Evidence Ledger；
- 保留该 Case 仍为 UNKNOWN / H 的关键边界；
- 把可迁移机制和不可复制条件分开。

### 可计算状态不要靠人工记忆

根 README 中“正式 Case 数 / Evidence Ledger 数 / Claim 数”来自 `metadata/`。`tools/reader_layer_lint.py` 在 CI 中检查这些数字以及正式 Case 的首页可达性，防止 README 再次停在旧阶段。

现阶段先检查漂移，不自动重写 README。等格式稳定、出现第二次重复维护成本后，再决定是否升级为 generator；不为了模仿别的仓库提前制造构建系统。

### 规则只在真实故障后升级

如果 reader layer 出现新的重复性错误，优先顺序是：

1. 修事实；
2. 记录为什么会错；
3. 能机械识别的才进 lint；
4. 不能机械识别的才进写作规则；
5. 不为尚未发生的问题预建复杂治理。
