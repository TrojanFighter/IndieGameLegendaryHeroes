# Temporal Validity Gate｜成功经验的年份与时效性

© 2026 洪荒行者。All Rights Reserved.

本项目禁止把历史成功案例写成无日期的“最佳实践”。

任何可迁移经验都至少回答四个问题：

1. **Observed When / 发生于何时？** 记录真正发生作用的年份，不只写作品发布日期。
2. **Regime / 当时处于什么生产制度？** 工具、平台、支付、发行、算法、社区、硬件、劳动力市场、生活成本与竞争密度是什么样。
3. **Mechanism / 真正可迁移的机制是什么？** 例如“尽早获得真实玩家反馈”可能长期有效，但“2013 年官网 paid alpha + PayPal 直销”只是当时一种实现。
4. **2026 Transfer Status / 到 2026 还能怎么用？** 不允许默认仍有效。

## 状态标签

### DURABLE — 结构机制仍有解释力
机制不依赖某个已消失的平台表面。例：让 commitment 随证据升级、把强项变成项目高杠杆、失败后保留残值、尽早让核心假设碰到真实玩家。

`DURABLE` 不代表“照抄做法”。

### CONDITIONAL — 机制仍可能成立，但执行环境已明显变化
必须先重新核验当前平台、竞争和成本。例：2017–2019 Reddit / Imgur / Tumblr / Twitter 的视觉传播；2013–2014 YouTube 对 Factorio 直销的放大；早期 Steam / Greenlight / EA 的曝光条件。

### HISTORICAL — 主要作为历史机制参考
当年的具体路径已经很难直接复制。例：1990s BBS/shareware direct-order economics；early id 依靠当时 PC 技术 frontier 和 shareware 形成的特殊窗口。

### CURRENT — 已在最近 12–18 个月重新核验
只有真的做过当前资料核验才可使用，必须注明 `Verified: YYYY-MM`。

### UNKNOWN — 当前时效性尚未核验
如果一个历史成功经验还没重新核过，就写 UNKNOWN；不能因为它“听起来仍合理”自动升级。

## Reader-layer 标准写法

每篇 Chapter / Profile 若给出可迁移建议，文末应有：

| 历史做法 / 机制 | 观察年份 | 当时条件 | 2026 状态 | 今天真正值得保留的部分 |
|---|---:|---|---|---|
| The First Tree 用视觉短内容持续积累关注 | 2016–2019 | Reddit / Imgur / Tumblr / Twitter 生态、低预算 solo 视觉作品 | CONDITIONAL | 让项目强项天然适合被低成本展示；具体平台打法必须重核 |
| Factorio 官网 paid alpha / direct sales | 2013–2015 | pre-Steam 直销、YouTube/论坛、长期系统型 PC 项目 | HISTORICAL / CONDITIONAL | 市场接口可以同时提供 runway、反馈和验证；支付/平台实现不可照抄 |
| FTL 有限储蓄 → prototype → 外部信号 → 再加码 | 2011–2012 | PC indie、IGF、Kickstarter 上升期 | DURABLE | staged commitment；Kickstarter 本身不是永恒入口 |

## Case / Claim 规则

- Case 可以记录历史事实，不强制给所有事实贴时效标签。
- 一旦从 Case 推出 **Transfer / “今天值得学什么”**，必须给年份与时效判断。
- Claim 若跨越多个时代，应明确它是结构命题还是平台命题。
- 平台、算法、流量、买量、creator discovery、商店曝光、众筹规则、引擎成本等属于高时效变量，默认 `CONDITIONAL / UNKNOWN`，除非重新核验。
- 生活成本、福利、税制、融资环境同样属于时效变量。

## 禁止写法

禁止：

> 2019 年某开发者这样做成功了，所以今天应该这样做。

改为：

> 2017–2019 年，这个做法在当时的工具 / 平台 / 社区条件下发挥了什么作用？到 2026，哪些条件还在，哪些已经变了？

成功案例不是 timeless recipe。

它首先是：

> **某个能力结构，在某个时代条件下，找到了一次有效匹配。**
