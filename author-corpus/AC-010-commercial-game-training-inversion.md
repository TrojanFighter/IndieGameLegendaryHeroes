# AC-010 — 商业游戏训练反转：目标函数迁移、岗位能力与独立创作

- Type: A0 — Author-Origin
- Author: 洪荒行者
- Status: AUTHOR THESIS TO BE TESTED — NOT YET A FORMAL CLAIM
- Related: AC-003, AC-004, AC-007, AC-008, AC-009; CASE-028, CASE-030, CASE-038

## 原始命题

作者围绕中国商业游戏从业者转向独立 / premium 游戏提出一条需要单独检验的命题：

> **职业经验不是一个统一的“经验值”。当项目的目标函数发生变化时，旧生产体制中高度优化的能力可能正迁移，也可能失效，甚至负迁移。**

这里所谓“目标函数变化”，尤其指：

- F2P / live-service → premium / 买断单机；
- retention / LTV / payer conversion → 首次购买、完整体验、口碑与长尾；
- 持续活动与商业化内容 → 有限范围内的玩法密度与作者表达；
- 已验证 benchmark → 依赖新奇性、hook 与差异化的产品；
- 大组织分工 → 极小团队端到端 ownership。

因此，“做过很多年商业游戏”不能自动推出“更会做独立游戏”，反过来也不能推出商业游戏经验无用。真正需要问的是：

> **这个人过去被反复奖励、训练和考核的能力，在新的产品目标里是否仍然有效？**

## Commercial-Game Training Inversion / 商业游戏训练反转

工作定义：

> **当开发者从一种成熟商业生产体制迁移到目标函数显著不同的产品体制时，旧环境中被强化的部分启发式、流程和岗位习惯可能由优势转为约束；与此同时，底层工程、内容生产、工具、协作、审美或用户理解等能力仍可能继续正迁移。**

它不是“手游经验有毒”，而是一个 **capability × target-function fit** 问题。

## 可能正迁移的能力

以下只是待验证类别，不预设所有商业团队都具备：

- 工程可靠性与性能意识；
- 工具、管线与自动化；
- 高频上线、bug 修复、数据观察；
- 大规模内容生产经验；
- 跨职能协作；
- 美术、动画、叙事、UI 等专业技能；
- 真实用户服务经验；
- 对特定玩家群体的长期领域知识；
- 项目排期、版本控制与生产纪律。

## 可能发生负迁移的部分

### 1. Target-function lock-in / 目标函数锁定

如果岗位长期围绕留存、付费活动、Battle Pass、LTV 或 payer segmentation 被考核，那么当新项目真正需要优化的是“有没有新鲜体验”“玩家愿不愿主动购买和推荐”时，原有最熟练的局部优化不一定仍是答案。

### 2. Benchmark capture / 对标捕获

成熟商业组织常通过竞品、指标和历史案例降低决策风险。这个机制在可预测赛道上可能有效，但在差异化 premium 产品里可能把“已证明的答案”错当成创新项目的题目本身。

这与 AC-007 相连，但 AC-010 关注的是：**这种思维如何成为职业训练的一部分，并在换赛道后继续被携带。**

### 3. Full-stack blindness / 分工盲区

大组织中的优秀局部岗位可以长期不需要亲自决定：

- 产品到底为什么存在；
- 哪个机制应该删除；
- 玩家为什么愿意第一次点进来；
- 这个项目有没有资格继续做；
- 美术、程序、内容、市场之间如何重新交换成本。

极小团队则常迫使成员重新承担这些端到端判断。

### 4. Production-scale inheritance / 继承旧成本结构

如果开发者把原公司中“标准项目应该有”的系统、规格、人员、内容量和流程一起搬到小团队，就可能把组织历史形成的成本误认成产品本身的自然成本。

### 5. Service-game intuition in a finite product / 服务型直觉错置

持续运营产品容许通过长期活动、角色更新和经济系统逐步修复或扩展价值；premium 单机更依赖一个有限产品在购买窗口内形成清晰 hook、完整体验和口碑。这会改变“先做什么、什么必须首发、什么可以永远不做”的排序。

## 岗位差异假说：不是“程序员优于策划”

作者提出一个需要专门采样检验的岗位差异问题：一些从商业游戏体系出来、后来独立做产品的程序员 / generalist，是否更容易因为拥有原型实现能力而保留端到端 prototype ownership？

目前**禁止**把它写成：

> 程序员天生比策划 / 制作人更会做独立游戏。

更可检验的版本是：

> **岗位是否持续拥有“提出假设 → 做出可玩物 → 自己观察反馈 → 直接改产品”的闭环，可能比岗位名称本身更能预测独立开发迁移能力。**

程序岗位在某些组织里可能因为能够直接实现 prototype 而保留这个闭环；也可能完全相反——大型工程岗位同样可能高度专门化、远离产品判断。策划、编剧、美术或制作人只要拥有真实 prototype ownership，也完全可能形成同样能力。

因此未来比较时应记录：

- 岗位名；
- 实际决策权；
- 是否亲自做 prototype；
- 是否能直接接触玩家反馈；
- 是否承担商业指标；
- 是否负责 feature ownership；
- 是否有完整 ship 历史；
- 转独立后是否成为 generalist。

## 当前最强公开样本：CASE-038 / 《苏丹的游戏》

《苏丹的游戏》是目前最适合检验本命题的中国案例之一，因为团队在发售前后的公开访谈中主动比较了两种生产逻辑。

触乐 2024-10-25 对双头龙工作室的直接采访中，团队明确表示：

- 这是 9 人小团队；
- 此前在单机游戏领域经验有限；
- 希望先做一个约一年能够完成的小项目试水；
- 团队把创作自由、玩法和事件机制置于核心；
- 他们直接以过去手游工作为反例，指出策划用两周制作 Battle Pass / 付费活动，与在新项目中持续思考“怎样才好玩”带来的能力成长不同。

2025-04-14 触乐进一步追溯其前史：双头龙核心来自十字星工作室；后者曾扩张为约 200 人的手游公司、获得过亿元融资，但《螺旋圆舞曲2》失败后收缩到不足 20 人，剩余核心重新组成小团队。制作人远古之风回顾新项目时，明确描述了从商业项目的规范化管理转向“好玩就行”、给予美术和文案更大创作自由的变化。

这些材料足以证明：**至少存在一个中国团队公开感知并主动改变了旧手游生产逻辑。**

它还不足以证明：

- 商业手游训练通常导致负迁移；
- 小团队自由管理通常优于成熟制作流程；
- 只有失败过的商业团队才能成功转型；
- 程序员比策划更适合独立开发。

## 与中国国情母题的关系

AC-004 讨论范式、风险和注意力结构；AC-008 讨论外部出题与开放问题；AC-009 讨论分发体制如何塑造市场世界模型。

AC-010 补的是**职业训练层**：

```text
产业长期优化某类商业模型
↓
组织按该目标函数建立岗位、KPI、benchmark 与流程
↓
从业者在这些局部问题上变得非常熟练
↓
市场 / 平台 / 产品体制发生变化
↓
旧能力重新分化为：正迁移 / 无关 / 负迁移
```

因此，“中国为什么会出现一批经验丰富、执行能力强，却需要重新学习如何做 premium / 独立产品的人”可以变成可研究问题，而不是民族性或人格叙事。

## 外部证据要求

要把本命题从 Author-Origin 升级为跨案例 Claim，至少需要：

1. 多个开发者的直接转型复盘，而不是成功产品的事后猜测；
2. 同一团队转型前后的工作方式、目标和产品结果；
3. 不同岗位迁移样本，尤其程序、策划、制作、美术、叙事；
4. 正迁移与负迁移同时记录；
5. 失败对照：试图从商业游戏转 indie / premium、但仍然失败的项目；
6. 控制“只有不满旧体系的人才愿意接受采访”的选择偏差；
7. 控制团队规模、资金、发行、市场窗口和题材差异。

## 禁止推论

不得写成：

- “手游从业者不会做游戏”；
- “商业化和好玩天然冲突”；
- “数据驱动一定伤害创意”；
- “策划 / 制作人天然不如程序员”；
- “大厂经验对独立开发是负资产”；
- “中国从业者整体缺乏创造力”；
- “只要摆脱 KPI 就会产生好游戏”。

更稳妥的研究命题是：

> **能力的迁移价值取决于它过去服务的目标函数，与新项目目标函数之间的结构相似度。目标函数切换越大，越需要重新审计哪些职业启发式仍然有效。**
