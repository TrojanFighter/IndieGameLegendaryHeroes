## 命题摘要

作者在 2026 年关于做题式教育、游戏产业对标与组织立项的历史讨论中反复提出一个母模型：

> **外部世界先产生一个真实成功的“题目/答案”；本土组织随后把这个成功压缩成可复制的 benchmark，再把 benchmark 进一步转化为竞品表、立项模板、KPI、岗位能力模型、投资偏好与职业赛道。**

这个过程当前暂称：

`External Benchmark → Internal Standardization → Meta Convergence → Benchmark Lag`

即：

1. **外部出题**：某个产品/公司/平台用真实市场结果证明一个新方向；
2. **内部标准化**：组织把复杂成功原因压缩成可审查、可汇报、可复制的标准答案；
3. **版本答案化**：大量团队围绕同一套被证明过的 feature / monetization / visual / platform / genre 结构下注；
4. **Benchmark Lag**：当组织终于大规模复制时，市场环境、用户口味或竞争结构已经改变。

这不是“中国人爱抄”这种人格判断，而是一个需要被操作化的组织与资本配置假说。

## 和 AC-004“三座大山”的区别

AC-004 的“范式规训”问：

> 为什么异常方向难以在组织内部获得试错权？

本文件进一步追问：

> **那个被组织奉为安全答案的范式，究竟是怎样从真实成功变成标准化模板的？**

因此 `Benchmark-Meta Convergence` 更偏向一个动态过程：

```text
真实创新
→ 成功被观察
→ 成功原因被压缩
→ 内部可读性提高
→ 立项/投资/招聘围绕该答案集中
→ 同质供给增加
→ 原先的超额机会消失
→ 新成功再次成为下一轮答案
```

## 为什么游戏产业特别适合观察

游戏行业具有几个放大机制：

- 单项目周期长，导致复制存在天然时滞；
- 商业数据高度不透明，组织容易依赖公开成功对象做 proxy；
- 失败项目不可见，容易形成 survivorship-biased benchmark；
- 资方/管理者需要把复杂创意转成可审批语言；
- 招聘和绩效体系会围绕既有品类岗位固化能力结构；
- 一款爆款常同时改变 genre、art style、商业模式、平台和营销渠道，组织却可能只复制其中最显眼的表层变量。

## 与“做题”的真正连接

这里的“做题”不是勤奋、考试或专业能力本身。

它指一种目标结构：

> **评价标准由外部预先给定，个人/团队的主要任务是提高在既有评分函数上的表现。**

这在稳定问题上非常有效；但创新项目的问题通常恰恰是：

> **评分函数本身是否正确？题目是否值得做？有没有尚未被定义的新需求？**

因此本命题不是反标准化，而是研究：

- 什么阶段应该标准化执行；
- 什么阶段必须保留改写题目的权力；
- 组织是否把执行阶段的优势错误前置到探索阶段。

## 候选行业现象 / 案例池

以下只作为待核线索：

### 爆款后的品类潮 / “版本答案”

作者旧讨论曾以若干中国市场“某款产品爆发后快速集中对标”的浪潮作为直觉样本，包括生存建造、派对/社交、开放世界、类帕鲁等方向。

正式研究必须找到：

- 立项时间；
- benchmark 文档或开发者公开自述；
- 资金进入时间；
- 项目取消/转向时间；
- 最终上市时市场窗口是否已经变化。

不能仅凭题材相似判定“跟风”。

### Boundary / Outpost 等高规格项目

它们更适合检验另一种 benchmark：是否把成熟商业射击/3A production spec 当成默认目标函数，再由融资与组织扩张去补齐。

这与简单 genre imitation 不同，但同样可能出现：

`外部工业标准 → 内部能力清单 → 组织先行 → 产品被标准倒推`。

### Dyson Sphere Program / Chinese Online Game 等反方向候选

这些案例可检验：经验丰富的开发者是否主动拒绝标准组织形态，先定义自己能低成本解决的问题，再选择性借用成熟行业能力。

如果成立，它们可能构成 `Benchmark Use without Benchmark Submission`：知道行业答案，但不让答案替自己出题。

## 需要警惕的反例

对标并不天然错误。

- Rocket League 明显建立在 SARPBC 的前作知识上；
- Into the Breach、FTL、Gunpoint 等也都大量吸收既有游戏语言；
- 技术栈、UX、平台规范、网络基础设施等领域，复用成熟答案往往非常理性。

因此研究重点不是“原创 vs 模仿”，而是：

> **团队是否知道自己正在复用的是哪一层答案，哪些变量已经被市场验证，哪些仍需要重新发现。**

## 可观察指标

未来若升级正式 Claim，优先寻找：

- pitch deck / 立项文档中的 benchmark 数量与作用；
- “至少像 X / 必须达到 Y”之类的决策语言；
- 投资、招聘、团队扩张是否发生在核心需求验证之前；
- 产品从第一 prototype 到正式版是否越来越接近外部模板；
- 发布时距 benchmark 爆发的时间差；
- 团队是否有 kill / pivot 机制阻止版本答案时滞继续吞噬成本。

## Research Gate

升级成正式 Claim 前至少需要：

- 3 个有明确立项/对标一手材料的项目；
- 至少 1 个“对标成功”的反例，证明 benchmark 本身可以是高效知识压缩；
- 能区分 genre diffusion、合理竞争学习与组织性答案化；
- 能把开发周期造成的自然时滞与错误判断造成的 lag 分开。
