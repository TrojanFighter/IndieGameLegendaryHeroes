# CASE-025 — Bills Must Be Paid / Rike Games

- Case ID: CASE-025
- Subject: Bills Must Be Paid / Rike Games
- Related games: No Pain No Gain; earlier Rike Games mobile / web prototypes
- Period covered: 2019–2026
- Research status: RESEARCHING
- Last verified: 2026-10-04
- Related Claims: C002, C003, C004, C007, C009, C010, C011

## Why this case

《Bills Must Be Paid》很容易被压缩成一个符合 2026 年独立游戏传播口味的故事：

> 一对夫妻、两个人、没有发行商、没有外部融资，用七个月做出第一款真正的 Steam 游戏，首发不到 72 小时卖出十万份。

这个版本并不完全错，但它把最有解释力的部分删掉了。

Rike Games 的两位创始人 Roxy 与 Mike 从 2019 年开始一起做游戏。根据他们自己的 postmortem，在 `Bills Must Be Paid` 以前，他们已经经历约七年 mobile / web 开发、约四年 mobile publisher 合同生产、接近一百个 prototype / game、多个失败项目、自发行旧原型、浏览器平台分发，以及 `No Pain No Gain` 这次专门用于学习 Steam 的过渡项目。到 2026 年 1 月正式押注 `Bills Must Be Paid` 时，他们说自己只剩“几个月 runway”。

因此本案真正要检验的是：

> **“七个月两人爆款”到底有多少是七个月本身，又有多少其实是此前七年高频试错、平台迁移和失败资本被压缩进了这次生产？**

它还提供了一个非常少见的市场接入样本：团队公开记录了 Steam 页上线、早期 wishlist、原定四月发售、改做 demo、Trending Free、creator outreach、中国自然传播、Next Fest、付费广告失败、Steam 平台曝光和最终 61k+ launch wishlist 的连续链条。

## 1. Myth

### 神话 A：两个人七个月从零做出十万销量 Steam 爆款

七个月基本只描述最终项目窗口，不描述能力形成。

团队此前已经：

- 连续做游戏约七年；
- 经历大量商业失败；
- 以 mobile publisher 合同为生约四年；
- 高频制作简单 prototype；
- 自己处理 mobile / browser 发行；
- 有一个 10M+ web plays / 45 万+ mobile downloads 量级的自报前作经验；
- 专门把 `No Pain No Gain` 移植到 Steam 学平台。

所以 `Bills Must Be Paid` 更像一次**长期能力资本终于命中产品—市场窗口**，不是两名新人突然完成职业跃迁。

### 神话 B：没有 publisher / external funding，所以是“零资源”成功

Steam 上 developer 和 publisher 的确都是 Rike Games，团队也明确说没有外部融资。

但“没有发行商”不等于没有生产条件：

- 过去 mobile publisher 合同曾长期支付他们的生存成本；
- 后续旧作、mobile 和 browser catalogue 继续提供现金流；
- `No Pain No Gain` 提供 Steam 学习；
- 两位创始人本身是长期共同生活、共同工作的夫妻组合；
- 他们已有官网、Discord、YouTube、X、browser portals 与既有玩家触点。

真正可说的是：**最终 premium Steam 项目没有外部 publisher / financing；不能因此把此前所有资本、渠道和能力前史抹掉。**

### 神话 C：Demo 一发，Steam 算法就把游戏抬起来了

Demo 是关键转折，但不是单因果。

团队自己的记录同时存在：

- Steam Trending Free 的意外曝光；
- Reddit 帖子；
- itch / CrazyGames / Armor Games；
- 接近 1,000 个 creator outreach；
- Bilibili / 中国 creator 自然传播；
- 一次盗版事件及媒体报道；
- Steam Next Fest；
- release-date announcement；
- Steam Personal Calendar / upcoming visibility；
- launch 前最后一周 front-page ramp。

因此本案反而证明：**市场接入不是一个按钮，而是多个可控与不可控通道叠加。**

### 神话 D：坚持就会成功

开发者自己在成功 postmortem 里反复强调 “Keep Going”。这是真实主观经验，但作为解释模型太弱。

本案能观察到的更具体机制包括：

- 高频 prototype 训练；
- 失败后的技能保留；
- publisher 合同维持职业连续性；
- 被 publisher 切断后改变收入结构；
- 用前作先学习 Steam；
- 对小核心 loop 极端 polish；
- 在低 wishlist 阶段主动改变发售计划；
- 把 demo 变成开发反馈与市场接入工具。

“坚持”只有在这些机制中才有解释力。

## 2. Origin

Rike Games 位于德国 Frankfurt。

官方 press kit 说明：

- 创始人为 Roxanne Góngora Alfonso（Roxy）与 Mike Niclas Gschwilm（Mike）；
- 两人是 Cuban-German married couple；
- 2016 年相识、2017 年结婚；
- 2019 年开始一起做游戏；
- Roxy 主要负责 art，Mike 主要负责 code / technical side；
- 两人会跨职能共同参与开发。

开发者自己的 2026 postmortem 对起点描述得更不浪漫：他们当时玩一款简单 mobile game，觉得“看起来不难，我们也能做”，于是直接开始。第一款 simple mobile game 做了约三个月，随后失败。

这个失败是后续生产史的真正起点，而不是 2026 年那次 Steam 立项。

## 3. Capability

### 高频 mobile prototype 是能力学校

团队说自己长期与 mobile publishers 合作，常见要求是：

- 一个月做 1–2 个 prototype；
- 快速形成玩法；
- 快速测试；
- 根据 KPI 决定继续还是 kill；
- 某些合同甚至采用“按交付 prototype 才付款”的强节奏。

到 2026 年，他们自报已经做过约 100 个 prototype / game。

这不意味着一百款商业成品，而意味着他们已经反复训练：

- 快速实现 core loop；
- 快速判断 feel；
- 小团队协作；
- art / code handoff；
- scope 压缩；
- build / publish；
- 失败后立即进入下一轮。

### 从 mobile / web 到 Steam 的平台迁移能力

团队在 2023 年末失去 publisher 后，开始自行把旧 prototype 包装成 mobile 游戏并投 browser portals。

随后 `No Pain No Gain` 在 web / mobile 得到较大规模传播。官方 press kit 直接把它定义为：

> the bridge to Steam

也就是说，他们没有把第一款真正想做的 premium Steam 游戏同时当作第一堂 Steam 课，而是先用较低风险前作学习：

- Steam page；
- build submission；
- demo / release；
- store mechanics；
- player behavior；
- PC packaging。

这一点对 C003 与 C011 很重要：**平台能力本身也是此前积累。**

## 4. Runway

本案目前不能给出可审计 euro budget，但能重建 runway 类型转换。

| 时段 | 来源 | 金额/口径 | 证据 | 置信度 |
|---|---|---|---|---|
| c. 2020–2023 | mobile publisher prototype contracts | 未公开；团队说长期依赖其付款生存 | E002 / E008 | 中 |
| 2024–2025 | 自发行 mobile + browser catalogue | 未公开；团队称整体收入“barely enough to keep going” | E002 | 中 |
| 2025–early 2026 | `No Pain No Gain` mobile/web/Steam + catalogue | 规模可见、利润未知 | E001 / E002 | 中 |
| Jan 2026 | 剩余内部 runway | 团队自报只剩几个月 | E002 | 中 |
| Jul 2026 后 | `Bills Must Be Paid` 销售 | 100k+ copies <72h 为开发者公开里程碑 | E002 / E005 | 中高（销量声明为第一方） |

关键点不是某一笔大钱，而是生产制度不断切换：

```text
publisher payments
→ self-published mobile/browser catalogue
→ Steam learning bridge
→ remaining internal runway
→ premium Steam launch revenue
```

这使它成为 C002 的一个好案例：**项目能活到爆发前，并不是因为某一轮融资，而是团队不断替换现金流来源。**

但目前仍未知：

- 家庭储蓄；
- 房租 / 生活 burn；
- publisher 年收入；
- browser / ads / IAP 收入；
- `No Pain No Gain` 的净收入；
- 是否存在家庭外部支持。

这些不能用首发销量倒推。

## 5. Production

### 核心团队

官方与开发者自述一致：

- Roxy：art 为主；
- Mike：code / technical 为主；
- 两人共同参与产品其他部分。

### 当前 contributor boundary

目前只能确认“两人 studio / 两人 core”，不能确认所有生产环节都只由两人完成。

尚未完成的 contributor audit 包括：

- music / SFX 来源；
- localization；
- QA / playtest；
- trailer / press assets；
- store art；
- middleware / asset-store content；
- external contractors；
- browser portal support。

所以正式表述应是：

> **two-person core studio / self-published premium release**

而不是：

> **all production done by exactly two people with no outside inputs**。

### 工具链

- Unity 已由 itch.io 与 SteamDB metadata 支持；
- PC / Mac Steam；
- HTML5 / browser build 也用于 demo distribution。

## 6. Scope

`Bills Must Be Paid` 的成功 scope 不是“内容很多”，而是**先把一个极窄的 tactile loop 做得非常明确**。

开发者回顾：

1. 先长时间 brainstorm；
2. kill 多个 idea；
3. 找到“砸 piggy bank 得钱”的 loop；
4. 先做一个只验证 mechanic 的极简 prototype；
5. 从一开始就追求这个动作的 polish；
6. 确认核心 feel 后，再讨论如何把 loop 扩成更完整 progression。

最终产品仍维持低概念解释成本：

- smash piggy banks；
- stamina；
- random loot；
- pay bills；
- perk / skill tree；
- bankruptcy / prestige；
- hammers / piggy variants。

这种 scope engineering 的关键不是简单地“做小”，而是把大部分生产资源集中在一个**无需复杂教程就能被视频、demo、stream 立即理解**的动作上。

这是 C007 的较强候选，但仍需要避免事后把“简单可传播”说成充分成功条件。

## 7. Failure

### 2019：第一款 mobile game 失败

团队把它明确描述为失败。

### 之后多年：大量 prototype / game 没成为 hit

团队直到 `Bills Must Be Paid` 才把它称为第一款真正 successful game。

### 2023：publisher 关系终止

这本来可能是职业中断，却逼迫团队从“为 publisher 产 prototype”转向：

- 自发行旧项目；
- mobile monetization；
- browser distribution；
- 自己建立平台关系。

### 2026：险些用 mobile 世界模型过早发售

这是本案最有研究价值的失败未遂。

早期 Reddit 帖显示，当时只有约 200 wishlist，团队仍在认真考虑一个月后直接 full launch，理由之一是担心 incremental wave 很快饱和。

他们后来自己承认：如果按原计划四月直接上线，不仅游戏没准备好，商业上也可能是灾难。

最终做法是：

> **原定 full release → 改成 polished demo → 继续收反馈、积 wishlist、参加 Next Fest → 七月正式上线。**

这个 course correction 比结果本身更适合支持 C009：**从 mobile 继承来的正确经验，到了 Steam 可能成为错误模型。**

## 8. Market

这是目前 corpus 中市场路径记录最细的案例之一。

### Steam page：尽早上线，但最初几乎没有 traction

团队自报：

- 2026-02-14 上 Steam page；
- day 1：11 wishlist；
- 后续通常 1–7 / day；
- Feb 14–Apr 20：528 total wishlist。

这直接反驳“挂 Steam 页就会自然长”的简化叙事。

### 早期 Bilibili organic pickup

一个 Bilibili creator 自然发现 trailer，带来一次小但可测的 wishlist spike。

它的研究意义不是“去 B 站就会爆”，而是：

> **公开页面 + 可传播物料会制造被随机发现的机会。**

### Demo：既是市场物料，也是生产工具

团队把原定四月正式版改成 demo。

之后：

- Steam Trending Free 出现约 340 CCU；
- 玩家评论与 Discord feedback 进入 full game 改进；
- demo 后 wishlist/day 大幅抬升；
- Steam demo lifetime unique users 最终自报 80k+。

因此本案里的 demo 不能只算 marketing asset，它同时承担：

- validation；
- playtest；
- polish pressure；
- community formation；
- creator playable build；
- Steam algorithm surface；
- wishlist conversion surface。

### Creator outreach

团队说在 Next Fest 前累计联系接近 1,000 个 creators。

但他们自己也强调 attribution 很差：

- 很多人不回邮件但会发视频；
- 有些是 organic；
- 有些来自观众推荐；
- creator 之间可能相互跟进。

因此“发 1,000 封邮件 = 61k wishlist”是禁止推论。

### Browser portals

他们把 demo 投到：

- itch.io；
- CrazyGames；
- Armor Games；
- 其他 browser 环境。

这扩大了试玩面，但团队认为部分 portal 到 Steam wishlist 的转化较低。

### China：重要但高度不可复制的右尾链条

团队先后经历：

- Bilibili creator 自然拾取；
- 中国玩家 / creator 关注；
- 未发售游戏被 decompile / reupload；
- piracy story 被媒体报道；
- 后续 creator 再次传播。

这是典型 Luck + Market coupling：团队能做的是让产品可见、可试玩、可分享；“盗版事件变成新闻”不是可以计划复制的 acquisition tactic。

### Steam Next Fest

团队自报：

- 进入 Next Fest：15,623 wishlist；
- Fest 期间新增约 7k，包括相关媒体覆盖。

同一团队另一款只有约 800 wishlist 的游戏参加 2026 February Next Fest，最终只增加约 173 wishlist。这个自我对照说明：**Next Fest 的结果强烈依赖进入活动前的产品 / audience 状态，不能当固定倍率。**

### Paid ads

Reddit ads：

- USD 200；
- 19 tracked wishlist；
- 没看到持续抬升。

至少对这款游戏，这次小规模 paid experiment 明显弱于 organic / demo / creator / platform exposure。

但不能外推成“Steam 游戏都不应该买量”。

### 最终 pre-launch ramp

Steam 官方 developer news 在 launch 前 7 天记录 40k+ wishlist；团队 launch-day postmortem 报告最终 61k+。

团队认为 Steam Personal Calendar / front-page upcoming exposure 对最后一段 ramp 很重要，但这仍是观察性归因。

### Launch

- 2026-07-29；
- USD 6.99；
- launch discount -30%；
- 2026-08-01 Steam developer news：100k+ copies in <72h；
- Reddit postmortem：67 hours / 101,079 copies / 1,800 reviews / 97% positive。

精确 units 是 first-party claim；SteamDB 的后续 review scale 与活跃数据只做量级 corroboration。

## 9. Environment

### 德国 / Frankfurt

目前还没有足够材料证明：

- 德国福利；
- 医疗；
- 住房成本；
- 创业补助；
- 家庭资产；

在本案中具体承担了多少 downside protection。

因此不应因为 studio 位于德国就自动把成功解释成“福利国家 advantage”。

### 夫妻两人团队

共同生活 + 共同创业很可能降低一部分沟通成本，也可能集中家庭财务风险。

目前只确认两人是夫妻与共同创始人；不推断家庭资金结构。

### 全球平台环境

团队能连续使用：

- mobile stores；
- browser portals；
- itch；
- Steam；
- Reddit；
- YouTube；
- Bilibili / China creator ecosystem。

这使他们能在 publisher 关系结束后重新组合 distribution，而不是必须重新进入另一家 publisher 的封闭供应链。

## 10. Luck

本案至少有四类不可直接控制的右尾事件：

1. Steam demo unexpectedly 进入 Trending Free；
2. Bilibili / 中国 creator 自然发现；
3. piracy incident 变成媒体 story；
4. launch 前 Steam platform surfaces 与 creator cascades 的具体强度。

团队能控制的是：

- page 存在；
- demo 可玩；
- product feel；
- creator outreach；
- release timing；
- follow-up material；
- feedback response。

团队不能控制的是：

- 哪个 creator 会捡；
- Steam 何时给多少曝光；
- 一次盗版事故是否变成新闻；
- audience cascade 到底扩大几倍。

因此应把“可重复准备工作”和“右尾放大事件”分开记录。

## 11. Verdict

### 成立

- Rike Games 的核心确实是两个人；
- premium Steam 版本确实 self-published；
- `Bills Must Be Paid` 的最终项目周期约七个月；
- developer-announced launch milestone 确实达到 100k+ copies <72h。

### 部分成立

- “没有 publisher / external funding”：对最终 Steam 项目成立，但忽略此前四年 publisher-backed production career 与旧作现金流。
- “first Steam game”：更准确应说 first premium Steam release；`No Pain No Gain` 已经先被移植到 Steam 学平台。

### 被证伪 / 高度误导

- “七个月从零学会做游戏”；
- “没有营销”；
- “Demo / Next Fest 单独制造了成功”；
- “十万销量证明坚持本身就是充分解释”。

### 无法验证

- 精确 budget；
- 净利润；
- household burn；
- 各市场渠道的 causal contribution；
- 全部 contributors。

## 12. Transfer

### 1. 把失败项目当 capability inventory，不只当 sunk cost

适用条件：每一轮 prototype 都真的留下技能、工具、判断或发行经验。

### 2. 大项目之前先做低风险 platform-learning project

`No Pain No Gain → Steam` 的价值在于，把商店、build、平台流程的学习成本与真正押注的 premium title 分离。

### 3. Steam page / playable demo 要尽早制造“被发现接口”

不是因为页面自动带流量，而是因为没有 public artifact，creator、平台算法、玩家社区都无法形成偶然发现。

### 4. Demo 可以同时承担 development 与 market function

前提：demo 本身足够 polished，且团队真的能处理反馈。

### 5. 在 launch plan 证据变差时，允许改变世界模型

团队原本准备四月上线。最终最关键的生产决策之一，是承认 mobile-style fast launch 假设不适合当前 Steam 项目。

### 6. 把 creator outreach 看成概率分布，不看成采购单

大量 outreach 的实际效果不可线性预测；重点是增加 exposure surface，而不是把回复率当成功率。

## 13. Non-transfer

不能直接复制：

- 夫妻共同创业结构；
- 七年累积的 tacit knowledge；
- 四年 publisher prototype training；
- 约百个 prototype 的失败资本；
- 中国 creator / piracy-news 右尾事件；
- Steam Trending Free / Personal Calendar 的具体曝光；
- 2026 年 incremental market 时点；
- 极高工作强度。

特别禁止把“almost every waking hour”写成 production best practice。这只是团队自述的投入强度，同时伴随明显健康 / burnout 风险，且不是因果可识别变量。
